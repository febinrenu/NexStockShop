# TrippleShop 2.0 — Storefront (Person B)

The customer-facing, multi-tenant storefront: every NexStock reference
page rebuilt against Person A's Laravel commerce API, a runtime theming
system covering all 27 reference visual styles, and bilingual
English/Arabic support with full RTL layout mirroring. This is the
Person B workstream from the TrippleShop 2.0 project brief — it consumes
the API that Person A's `backend/` folder implements and builds nothing
of its own on the server side beyond a thin proxyless client layer.

## Stack

- Next.js 16 (App Router, Turbopack, React 19, TypeScript)
- Tailwind CSS v4 (CSS-first `@theme`, no JS config file)
- [`next-intl`](https://next-intl.dev/) — locale-prefixed routing (`/en/...`, `/ar/...`), RTL
- [`openapi-fetch`](https://openapi-ts.dev/openapi-fetch/) + a client generated by `openapi-typescript` from Person A's committed `docs/api/openapi.json`
- Vitest + Testing Library (unit) / Playwright (E2E)

## Architecture in one page

**No server-side proxy to the API.** Person A's backend
(`stancl/tenancy`) resolves which tenant a request belongs to purely from
the raw HTTP `Host` header. If this app proxied API calls through its own
Next.js server, the outgoing request's Host header would be this server's
own hostname, not the shopper's tenant subdomain, and the backend would
resolve the wrong tenant (or none). Instead, every API call goes directly
from wherever it originates to the same host the page itself is being
served on: server components read the incoming request's own Host header
(`apiBaseUrlForHost()` in `src/lib/api/config.ts`), and client components
read `window.location.host`. There is no `/api/*` route in this app at
all.

**Theming is 27 real, ground-truthed token sets, not a placeholder
system.** `theme-registry.raw.json` holds one entry per reference theme
(colors, fonts, shadows, computed surface/ink pairs), extracted from the
original static NexStockShop `themes/*.html` mockups by
`scripts/build-theme-registry.py`. Critically, each theme's `primary`/
`primaryDark`/`accent` roles were **not** guessed from color key names
(e.g. assuming a key called `navy` is the primary action color) — the
script's `ROLES` mapping was built by grepping each mockup's own hero CTA
markup ("Shop Now", "Subscribe", search-button fills) to find which
`bg-brand-*` color the mockup's own author actually used for real primary
actions. This caught several wrong initial guesses (naturae's true
primary is `green`, not `greenLight`; marketverse's is `orange`, not
`red`; voguelane's is `black`, not `red`) — see the `ROLES` dict's
comments in the script for the full list.
`scripts/build-theme-tokens.py` turns that registry into
`src/styles/theme-tokens.css` — one `[data-theme="slug"] { --theme-*: ...; }`
block per theme — which `globals.css` maps into Tailwind's own
`--color-*`/`--shadow-*`/`--font-*` namespace via `@theme inline`, so
ordinary utility classes (`bg-primary`, `text-ink`, `shadow-card`) render
correctly for whichever theme is active. The root layout sets
`data-theme` on `<html>` per request from the tenant's
`branding.theme` (`GET /api/v1/settings`). A `:root:not([data-theme])`
fallback block exists for the (rare) case of a non-tenant-scoped page —
it is deliberately **not** a bare `:root`, because `:root` and
`[data-theme="X"]` have equal CSS specificity and a bare `:root` placed
after the theme blocks in source order would silently win the cascade
for every tenant regardless of which theme was actually active. That
exact bug shipped once during development and was only caught by loading
the app in a real browser — see the comment above the fallback block in
`src/app/globals.css` and `theme-registry.test.ts`.

**Hand-declared types where the generated client can't help.** Person
A's OpenAPI spec is generated by `dedoc/scramble`, which can't infer a
response shape from a controller that does
`response()->json($eloquentModel)` directly — those endpoints come out of
`openapi-typescript` typed as `unknown`. Rather than losing type safety
on exactly the endpoints that matter most (cart, checkout, orders,
addresses), `src/lib/api/raw-types.ts` and `src/lib/api/product-types.ts`
hand-declare accurate interfaces from direct inspection of the backend's
models/migrations/controllers, and call sites cast narrowly
(`as unknown as X`) with a comment explaining why. Request params with
unreliable generated types are cast `as never` at the call site rather
than loosening the underlying generated `schema.ts`, so a real backend
contract change still shows up as a diff when `schema.ts` is
regenerated.

**Multi-currency.** Every price from the API is a currency code plus a
minor-unit integer, matching the backend's convention exactly — this app
never turns a float back into minor units, only formats the pair
(`formatMinor()` in `src/lib/money.ts`). The shopper's currency choice is
mirrored into a cookie (`trippleshop_currency`) alongside client state so
server components can fetch prices in the right currency on first
render, and `router.refresh()` re-fetches server data when it changes.

**Guest carts.** A guest cart is identified by an `X-Guest-Token` header.
The token is minted by the backend and returned in the cart response
body's `guest_token` field (not a response header), captured by an
`openapi-fetch` middleware (`src/lib/api/client-browser.ts`) and persisted
to `localStorage` for subsequent requests. **Known gap, not fixed here:**
the backend's `CartController::resolveCart()` switches entirely to
`customer_id`-based resolution once a shopper authenticates, with no
merge step — a guest who adds items, then registers mid-session, loses
that cart. This is a common e-commerce gap that needs a backend change
(merge-on-login) outside this workstream's scope; it's called out here so
it isn't mistaken for an oversight.

**i18n/RTL.** Routes are locale-prefixed (`/en/...`, `/ar/...`) via
`next-intl`'s middleware (`src/proxy.ts` — Next.js 16 renamed
`middleware.ts` to `proxy.ts`). `messages/en.json` and `messages/ar.json`
are real, professional translations, not placeholders — key-parity
between the two is enforced by `src/i18n/__tests__/messages.test.ts`, and
a full RTL layout check runs in `e2e/rtl-locale.spec.ts`. Almost the
entire app uses logical CSS properties (`ps-`/`pe-`/`text-start`/etc.)
so it mirrors correctly with zero direction-specific overrides; the one
narrow `[dir="rtl"] .flip-rtl` rule in `globals.css` exists for the rare
element (a directional icon) that logical properties can't handle.

## Directory layout

```
src/app/[locale]/            All 15 pages: home, shop, product detail, cart, checkout,
                              login, register, account, wishlist, track-order, order detail,
                              deals, brands, about, help — locale-prefixed by next-intl.
src/app/[locale]/layout.tsx  Root layout: resolves locale + tenant settings + currency,
                              sets <html lang dir data-theme>, wraps providers/Header/Footer.
src/components/catalog/      ProductCard, ProductDetail, ReviewList, ShopFilters, PriceTag, CategoryTile
src/components/layout/       Header, Footer, CartIcon, CurrencySwitcher, LocaleSwitcher, SearchBar
src/components/providers/    AppProviders — composes Currency > Auth > Cart context providers
src/lib/api/                 Typed API client: schema.ts (generated), catalog.ts (server),
                              commerce.ts (client), raw-types.ts / product-types.ts (hand-declared),
                              config.ts (per-request tenant host resolution), storage.ts (token persistence)
src/lib/store/                CurrencyProvider, AuthProvider, CartProvider (React context, not a global store lib)
src/lib/tenant.ts            GET /api/v1/settings wrapper with a graceful fallback
src/lib/money.ts             formatMinor() — the one place minor-unit amounts become display strings
src/i18n/                    next-intl routing, navigation, and request config
src/proxy.ts                 next-intl's routing middleware, under Next 16's renamed convention
src/styles/theme-tokens.css  Generated — 27 [data-theme="slug"] blocks (do not hand-edit, see scripts/)
theme-registry.raw.json      Generated — the ground-truthed per-theme token registry (do not hand-edit)
scripts/build-theme-registry.py   Regenerates theme-registry.raw.json from ../themes/*.html
scripts/build-theme-tokens.py     Regenerates theme-tokens.css + src/lib/themes/list.ts from the registry
e2e/                          Playwright specs against a real running backend + seeded tenant (see e2e/README.md)
```

## Local setup

```bash
npm install
cp .env.local.example .env.local   # if present; otherwise create it, see below
npm run dev
```

`.env.local`:

```
NEXT_PUBLIC_API_SCHEME=http
NEXT_PUBLIC_API_PORT=8000
NEXT_PUBLIC_CENTRAL_HOST=localhost
```

This assumes `backend/` is running locally on port 8000 with at least one
tenant signed up (see `backend/README.md`'s "Local setup" section). Visit
the tenant's subdomain directly, e.g. `http://acme.localhost:3000/en` —
not `localhost:3000` — since the tenant is resolved from the request Host
header exactly as it will be in production.

### Regenerating the API client

Whenever `backend/docs/api/openapi.json` changes:

```bash
npx openapi-typescript ../backend/docs/api/openapi.json -o src/lib/api/schema.ts
```

Re-check `raw-types.ts`/`product-types.ts` against the backend source by
hand afterward for any endpoint the generator can't type — it won't flag
those itself.

### Regenerating the theme registry

Only needed if the reference mockups in `../themes/*.html` change, or a
new theme is added:

```bash
python3 scripts/build-theme-registry.py ../themes
python3 scripts/build-theme-tokens.py
```

Adding a new theme requires adding its `(primary_key, primary_dark_key,
accent_key)` ground-truthed role mapping to the `ROLES` dict at the top
of `build-theme-registry.py` — the script deliberately refuses to guess
and exits with an error naming the theme if it's missing.

## Testing

```bash
npm run lint        # eslint
npx tsc --noEmit    # typecheck
npm run test        # vitest — money formatting, theme-registry integrity, i18n key parity
npm run test:e2e    # playwright — requires a running backend + seeded tenant, see e2e/README.md
npm run build        # production build
```

The unit suite (`npm run test`) is hermetic and covers: `formatMinor()`'s
currency-formatting edge cases (including its ICU-throws fallback path),
that all 27 themes in the registry have complete, valid-hex token sets
whose `primary`/`accent` really do trace back to the mockup's own color
map (not a guess), and that `messages/en.json` and `messages/ar.json`
have identical key sets with no untranslated placeholders.

The E2E suite (`npm run test:e2e`) is **not** hermetic — it drives a real
browser against a real running backend and a seeded tenant, because that
is what actually caught the two real bugs in this codebase that
`tsc`/`eslint`/`next build` did not: a CSS specificity bug that silently
replaced every tenant's theme colors with the generic fallback, and a
checkout-confirmation screen that rendered as "your cart is empty"
immediately after a real order was successfully placed (the
order-clears-the-cart side effect was tripping the same empty-cart guard
that protects the earlier steps). Both are fixed and both are now
regression-tested in `e2e/checkout-flow.spec.ts`.

## Known limitations

- **Guest cart is not merged on login** — see the "Guest carts" section
  above. Needs a backend change (`CartController::resolveCart()` merge
  logic), out of scope for this workstream.
- **Guest checkout does not persist the shipping address.** The backend's
  `addresses` table requires a non-nullable `customer_id`, so a guest's
  address is collected and used for the checkout session's
  `shipping_address_id` only when the shopper is logged in; a pure guest's
  address fields are for display/completion of the checkout form only.
  Logged-in checkout saves the address via `POST /me/addresses` first.
